## 四、沒有解決的

- **第一張工單逾時**:45 到 53 分。時間多在少數幾次長思考(f7-17 的 B1:49 分裡 40 分在 10 次思考、約 25 萬字,實際寫出的腳本與指令約 3 萬字),而且同一張工單內重複從頭分析好幾次(前面的思考不留在對話歷史裡)。錯誤其實在約 25 分時就確定了,其餘時間在架正式比對、開關、報告。
- **Qwen 自己架比對的自由度太高**:設暫存器(`hold`、`start=`、`state=`)、訊號命名、驅動埠各有多種寫法,主機檢查一再對不上。
- **工具使用不穩定**:有的工單完全不用 `piececheck`,結果仍對,但沒有紀錄可查。
- **A 與 B 重工**:A 已逐行翻譯 RTL,B 每張仍重新讀 RTL、重列片段。A 的工單要求的片段清單(讀哪些訊號、寫哪些訊號)沒有落實成 B 可用的資料。
- **不屬於單一片段的錯**(先讀後寫)完全依賴工單要求整段跑。

## 五、由此得到的方向(討論中,尚未實作)

找錯的能力已經夠(索引、方向、條件類幾乎不失手),瓶頸在比對的架設與重複推導。2026-11-25 與使用者討論的新流程:

1. Qwen 依自建的參考模型寫區塊框架 JSON(以 json map v3 的框架為標準比較)。
2. Qwen 讀整份 RTL 做對齊(RTL map);RTL 整份給,不拆小段。
3. A 照 map 把 RTL 轉成 Python。
4. B:一張工單一個功能,順序與 data chain 一致;找 bug、加開關、記帳本;每次比對完由主機確認入帳,帳本只告知「RTL 哪一段是什麼功能,已確認」。
5. UD、UC 照舊;未知數是由 map 轉出的 Python 對 UD、UC 的影響。

可行性實驗(haiku 扮演 Qwen)在 `runs/dry_aes0005/dry-aes0005-MAPFLOW-01/`(不在 git 內),結論另行記錄。
