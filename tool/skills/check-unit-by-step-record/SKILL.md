---
name: check-unit-by-step-record
description: Find the faults in the data path, the control and the handshake of ONE module of a hardware design that has a start and an end (an operation of several clock edges), when the reference model gives a record of steps for one operation. The measuring is done by two libraries on the design's Python translation; stepfacts sets the data register to each step of the record, forces every control value and runs one edge, so it says whether a fault is in the data path or in the control, at which step or edge; hsfacts compares the ports with a timed specification model. Each fault is repaired with a switch that is judged by running the library again. Used after the pieces of the module were checked alone and the modules below were checked as units.
---
Principle. Reading gives a hypothesis; running gives a fact. The measuring is done by the libraries, the same way every time: you do not write a checker, a driver or a table. What is left for you: describe the unit once, read the print, find the statement behind ONE difference, prove it with a switch, run again.

The blocks of a unit. The data path: what the data register takes in one edge for each value of the control registers (which operations, with which parameter). The control: which value the control registers take next. The handshake outputs: what the end signal and the result ports show. A unit below is a block that was checked before; its result is taken as right once it has finished. The data path is judged first and alone, with the control registers forced; the control is judged with a data path that is right; the handshake last.

1. The description. Write /code/work/handshake.json as the texts at the top of /code/lib/hsfacts.py and /code/lib/stepfacts.py say: the start input, the end output, the result outputs, every mode in which an operation can be started, two sets of data, the control registers, the ONE data register the record describes, the register this unit reads from each unit below, and a tail longer than the longest operation. A mode whose result is defined only after an operation in another mode is named in "needs_before". Names are the names sigdump prints; do not guess a name: run and read the print. A register you add to the control later is added to "control".
   The record of steps: a small file with one function, as the text of stepfacts says, that calls the reference model's function for the whole operation in its form that returns the step record, and returns the list of states. It contains no operation of its own. For a mode that uses what an earlier operation stored, it takes that from the operations given in `before`.
   Entries the host gives (the timed specification model) are not written by you; they are in /code/work/spec/given.json and the libraries read them there.

2. Read a print of stepfacts from the bottom: the last lines say how many differences part 1 and part 2 have; then the lines of the first difference. When the first lines say that no edge hits the record in any arrangement, the description or the record file is wrong, not the design: repair that first.

3. Part 1, the data path (the control is not looked at). First read how the design cuts the record into edges: one edge of a design usually applies several operations of the record, and the print says at which steps its edges start and end (from the hits, and from the near hits: an edge that gives the value of a later step but for some elements does the operations up to that step and has a fault in one of them). The data register is not expected to hold every step of the record; it holds the steps at which edges end. A step from which NO control value goes on is a fault of the data path at this step: with the data of that step in the register, no value of the control makes one edge produce a later step of the record.
   - A reached step at which no edge starts: the print says where the next edge starts and which operations of the record lie between; the edge from this step applies exactly these. A piece of the chain that does an operation which is not among them is applied where the record does not apply it.
   - A NEAR line: the edge applies the right operations and one of them is wrong in the named number of elements; its detail shows which piece.
   - Run `--step K` for that step. For every control value it prints what the edge does and, for every piece of the chain, the step of the record that piece holds after the edge. Read the pieces in the order of the chain (the order in which the source feeds one piece into the next; the print lists them in the order of the model) for the control value that should do the step: the pieces hold the steps K+1, K+2, ... one after the other up to some piece; the first piece that holds no step, or a step that does not follow, is where the chain leaves the record. A piece printed with some elements unknown read, in this evaluation, something that the source writes later (the order of the statements inside a loop); the named elements say which. "nearest is step J, some elements differ" means this piece does the operation of step J and is wrong in the named elements only (look at what these elements have in common: their index, the order in which the source writes them); a piece that holds a step the record applies elsewhere is applied where the record does not apply it, or with another parameter (an index, a key, a constant).
   - The control value that should do the step: the one for which the first pieces of the chain hold the next steps; else the value the design itself has there in part 2, or the value that does the neighbouring steps. The statement that decides the piece found above, for this control value, is the candidate. Write it as a switch that changes this one place, in the source's form, with a name in `fix`. With no switch on, RtlModel still does what the RTL as written does.
   - Run stepfacts with the kept switches and the candidate (`--fix all,candidate`). Keep it when a control value now goes on from this step and no step that went on before is lost. A candidate is not accepted and not rejected by thought.
   - When two candidates give the same print, take the one that changes less of the source and say that the other exists.
   - A switch of an earlier order that a print shows to be incomplete (it repairs a piece alone, and the piece is still wrong in the chain) is corrected in its place under its name; a second switch on the same source lines is not added. It is tried by changing it and running with `--fix all`; the commands or scripts the earlier report names for checking this piece alone are run once more with the changed switch. Say in the report that the earlier switch was changed and why.
   - The design may apply several operations of the record in one edge, or cut them at other points than the reference: that is no difference. What counts is that from every reached step some control value reaches a later one, up to the final step.
   - Part 1 is finished when the final step is reached from the load and no reached step is without a control value that goes on. Only statements of the data path are changed for part 1: what a control state applies to the data and which parameter it selects. The next value of a control register is not changed here.

4. Part 2, the control (after part 1 is finished). The design runs by itself; every edge is judged with part 1. One difference at a time: the case without a start first, then the cases with one operation, then with two; in a case the first difference.
   - A difference marked CONTROL names the control values that would have gone on, or would have kept the data, at this edge. The control register had another value there: find the statement that gave it this value in the edge before (a condition, a compared value, a constant), and the statement that should have held or advanced it. Each place that could repair it is a candidate switch; run stepfacts with the kept switches and one candidate; keep the one with which this difference is gone and no edge that was right before is lost, in every case.
   - "no control value would go on at this edge" while the unit below is working: the unit must wait here. The control values that keep the data are printed; a candidate makes the control stay in such a value until the unit below has finished. Where to look: the end signal of the unit below and what already reacts to it in this unit; a signal of the unit below that is not yet a port (one switch then names the new output of the unit below and every place that uses it; in the model the register of the lower object is read and the comment gives the RTL text of the new port).
   - "changes after the final step" or "changes without a start": the control leaves, or does not return to, a value that keeps the data.
   - A difference marked DATA PATH in part 2 that part 1 did not show belongs to a mode or a second operation: run part 1's detail for that step and treat it as in 3.
   - When two candidates give the same print, take the one that changes less of the source and say that the other exists. From less to more: a constant or a condition of an existing statement; a signal that exists and was not used; a new signal or port taken from the unit below; a new register.
   - A candidate that changes a statement on which a kept switch already sits is run without that kept switch: name the other kept switches and the candidate (`--fix a,b,candidate`); with `--fix all,candidate` the kept switch may decide the statement and the print is then the print of `all`. Read the first line of the print: it names the switches that were on.
   - A register that a candidate adds to the control is added to "control" in the description before the candidate is measured.
   - The code of a candidate that is not kept is taken out of the model when the choice is made (its name, place and print lines stay in the book of the switches, as dropped): in RtlModel `fix="all"` turns on every name the code asks for, also one that is not in `SWITCHES`, and the orders after this one run the model that way.
   - A kept switch is not opened again unless a print shows a difference because of it. After a switch is kept, add it to `SWITCHES`; `--fix all` then means the kept switches.

5. The handshake (after part 2 has no difference). Run hsfacts: the ports of the design next to the timed specification model, case by case. The lines marked DIFFERENT are the differences; a line marked "(a count)" differs only in the number of edges and is a difference only when a sentence of the task text or of its documents states the number; the numbers of edges in the schedule of the timed specification model are that model's own choice and are not repaired. What is still wrong here is in the statements that give the end signal or the result ports their value, or in which control value the unit waits (two ways of waiting can both keep the data and differ in what the end signal shows meanwhile): candidates as in 4, judged by hsfacts and by stepfacts together: a candidate is kept only when the hsfacts line becomes "same" and stepfacts still prints no difference. A case that hsfacts prints as not compared because of the specification model is written in the report and left: the specification model is not changed or replaced in this work. A start while the unit is busy is printed and not compared unless a sentence says what must happen.

6. The book of the switches and the report. Both libraries append the end of every print to /code/work/tool_runs.log: read its last entries first when the work is continued, they are the state. Write each kept switch (source file, lines, the run and the difference it removed) in the book of the switches when it is kept, and each candidate that was removed, with the library the order names for it; when the library reports an entry at the same lines, decide which holds before going on. The report: the description, the differences of the first print, each switch, and the last lines of the last print of each library the order uses. When the handshake (point 5) is part of the order, also what this unit gives a reader of its ports: which signal says the end, after which edge, and what is complete from then on.
