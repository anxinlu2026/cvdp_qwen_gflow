---
name: check-pieces-against-spec
description: Find the faults inside the pieces of a hardware design with its executable Python translation: each piece is run alone on the same inputs as a reference written from the specification, the first wrong part is traced to one statement, and a switch that changes one place proves the fault.
---
Work in this order.

1. Principle. Reading gives a hypothesis; running gives a fact. A piece is judged alone: the same inputs go into the piece of the design and into a reference for that piece, and the outputs are compared. In which cycle the piece is used, and what the other pieces do, play no part in this judgement. The inputs a piece gets are the values in the form the design gives them to it: the output of the piece or submodule that produces them, in that one's arrangement, and one call (one edge) as the design uses it. If a piece agrees only when its input is rearranged or when it is called more than once, that need is itself a difference (point 6), not something to settle in the test.

2. List the pieces of the scope from the translation: name, source lines, inputs, outputs, and kind (combinational or register).

3. Match each piece to the reference model: the function of the reference model, or the part of one, that gives what the piece gives, and the step of the specification it belongs to. A piece may be one step, a part of a step, or several steps. A design may group and order the steps differently from the text of the specification; that is its choice and not a fault. Pieces that only bring data into or out of the design's internal arrangement (load, unload, select a part) are taken as a pair: bringing in and taking out must give back the input, and the arrangement between them must be the one of the specification (its rows, columns, word and byte order), because the other pieces work on it. Which index of the design's data is which index of the specification (row, column, word, byte) is decided by the pieces that compute along rows or columns (a piece that combines the elements of one column, a piece that moves the elements of one row), not by a piece that only brings data in or out: one of those may be the fault. With this arrangement each piece that brings data in or out is judged on its own against the formula of the specification; a round trip that does not give back the input says only that one of the pair is wrong. The arrangement is written once, in /code/work/arrangement.json: `{"place": the arrangement of the data arrays, "signals": {signal: its arrangement where it differs or where "place" does not fit its shape}, "basis": the pieces and lines that decide it}`; each arrangement is one of the names piececheck.place knows, and the description goes in "basis". The first order writes the file for the data arrays of its scope, and every later comparison uses it (piececheck.against takes it when `place` is not given). A later order whose scope has data arrays the file does not give adds them, decided in the same way; what the file already gives is not changed. A comparison with another arrangement compares nothing of the design: the reference model is the golden one, and the arrangement is not chosen to make a piece agree.

4. Reference: the function of the reference model in /code/work/model for the step (its notes list the checks it passed on the specification's examples; the order gives the host's run of these checks). A part of a step (a product, a partial result) is computed with the functions of the reference model (for example its multiplication), not with a formula of your own; a reference written from the specification is used only where the reference model has no function for it, and the report says so. A function that the notes list with no example is reported as "not checked on an example". Never change a reference to make a piece agree.

5. The model's values are `V` (library svvec); a reference works on integers. Run with /code/lib/piececheck.py (how: /code/lib/usage.md): `piececheck.against(model, hold, read, ref_function, inputs, place=...)` holds the signal that holds the input (or, for a piece that reads several signals, each of them at its value from a function of the reference model), runs one step(), reads the signal it names, and compares it with the function of the reference model on every input; `piececheck.text_against` prints the row of the table. A held signal that step() does not write is not what the piece reads (piececheck.run prints the count). `.int()` raises when a bit is X; an X element is printed as x: find the operand that is X (point 6). Write one table row per piece and per step (agree, or differ on how many inputs):
   - inputs: the states before each step that this piece or step computes in the reference model's step record (piececheck.befores(record, step)), with the record made by the reference model on the specification's example (its notes name it) and on random data, and at least 20 random inputs;
   - each step of the reference model's step record that the scope computes (its state before and its state after are signals of the scope) is also run as one, also when the design computes it with several pieces (point 3) and each of them agrees alone: hold only the signal that holds the state before the step, read the signal that holds the state after it, and let the pieces between them run as step() runs them. Holding the signals between them shows each piece alone, but not what one piece reads of another inside the same step(). When the step run as one differs from the reference while each piece held alone agrees, the step is a piece that differs (point 6), not a fault of the run: its first wrong part is read where one piece reads a signal that another piece of the same step() writes later (its value there is X or the value of an earlier pass), and the place is proven with a switch (point 7: the position of a statement relative to a loop or to another statement);
   - the data path from port to port, in the order whose scope has the pieces that bring the data into the design and take it out: with the arrangement of /code/work/arrangement.json, (a) drive the input ports that bring the data in (`inputs_ports`, a function of the input), hold nothing, read the register they load, and compare with the first step of the reference model's step record; (b) set the register that holds the state (`start=`) and read the same register after one step(): the steps of the reference model between these two states (also when the design groups them differently from the specification, point 3) run as one; (c) set the register and read the output port, compared with how the reference model takes the data out.

6. Locate inside each piece that differs, before you judge it:
   - find the first part of its output that is wrong;
   - take the statement that computes this part, print every operand it reads, and compare each with the operand the reference uses for the same part. If a wrong operand is computed inside the piece, go to its statement and repeat. The place is the statement that reads the wrong operand (a wrong index, element or bit) or gives a wrong result from right operands.
   - "The structure is wrong" or "one change cannot repair it" is not a result. The result is the first wrong part and the operand table.

7. Prove the place with a switch. A switch changes one place: one operand, index, condition or constant, the position of a statement relative to a loop or to another statement, or one added condition that makes a statement not apply in a named control state (the same kind of change on parallel lines is one switch). It is written in the source's form, has a name in `fix`, and with no switch on the model is the design as written. Never replace a piece by its reference. With the switch on, compare again: if the part is now right the switch stays, and the next wrong part gets the next switch, until the piece agrees on all inputs; a switch that does not make its part right is removed.

8. Report: the table of pieces, the table of the steps run as one (the step, the signal held, the signal read, agree or differ), and for each switch the source line, the change, and the values of the part without and with it. Say which statements rest on a run and which on reading only.
