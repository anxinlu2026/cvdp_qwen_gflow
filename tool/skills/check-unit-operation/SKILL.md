---
name: check-unit-operation
description: Find the faults in the control and sequencing of ONE module of a hardware design with its executable Python translation, after its pieces were checked alone and its one-edge table was measured. The module is driven at its own ports. Part A checks the walk of its control registers and its handshake without looking at the data; part B builds the sequence of operations from the walk and the one-edge table, compares it with the specification's sequence, and then compares the values. Modules are done from the lowest upward: a module below that was done is taken as known.
---
Principle. Reading gives a hypothesis; running gives a fact. Work from the bottom: the pieces were checked alone (block_check), what one edge stores in each control state was measured (edge_check), the modules below were checked as units (unit_check). What is left for this unit is only: which control states it walks through, in which order, and whether it waits for what it needs. Do not check again what a lower step settled; when a result here contradicts a lower step, say which and stop there.

The unit is the module of the scope, driven at its own ports with your own Python scripts. A module below is inside it. What the unit needs from outside is given at its ports the way the specification says it arrives. The library sigdump runs a model or the class of a submodule on a list of steps (`sigdump.run`) and gives every signal before and after every edge; read the text at its top.

The requirement comes from the sentences of the specification and, for the handshake at the ports of the top module, from what the testbench does (how it starts an operation, what it waits for, when it reads the result). For a module below, the requirement is what the module above reads from it: read there which signal it waits for and what it uses after it. A reference model is used for values. The number of cycles a reference model takes is not a requirement unless a sentence of the specification states it.

## Part A — the walk (the data is not looked at)

A1. Cases, from the specification, for this unit: no start after reset; a start, in each mode of the unit, once in the first edge after reset and once after some edges without a start; a second start after the end; a start while busy (every start with data that differs from what the registers hold, so that a result that is not yet complete can be seen); for a unit that uses a unit below: each mode in which the lower unit must run first, and each mode in which it must not. Every case ends with edges without a start, at least as many as one walk takes, so that what the unit does after the end is seen.

A2. Run each case from reset and print per edge: the inputs, every control register of the unit and of the units below, and the handshake signals, before and after the edge.

A3. The walk checker. Before anything in the model is changed, write the points of A5 as a script. Build it in steps, each ended by a run: first the cases and the per-edge print of A2; then one point at a time: read in the print which records decide the point, add it, run. A point is not worked out in thought for all cases before the print exists. It takes the switches as its argument, runs every case of A1 from reset, and prints for every case and every point of A5 (P1 to P8) one short line: holds, fails at edge N (with the control registers and handshake signals at that edge), or no requirement; the long prints go to a file. For the top module one of the cases is what the testbench does, run with `sigdump.run` (its waits as `until` or `until_rise`). The checker reads the control registers, the handshake signals and "did this data register change" from the records; it does not contain a copy of the design's conditions: a handshake output is the value the model's step gives for this output, not a bit of a register that the checker (or an interface description) names itself. Say at the top of the checker which value an edge sees: the testbench or the module above sees at edge N the value from before edge N. A point is measured the way the source of its requirement observes it: when the testbench waits for a rise of the end signal and then reads the result, "a start is accepted" means that this rise comes after the start and "the end is signalled" means this rise; a signal the source does not look at (the edge in which a register leaves its idle value) is not part of the point. The level of the end signal is the exception, because others than this testbench read it: P6 says what it is in every edge. Whether a data register is kept or written in an edge is taken from the one-edge table for the control state of that edge, not from comparing values (a register may be written with the value it had). The switches are given to the checker as a list of names, so that it can run with the kept switches and one more. Run it with the switches found so far. The points that fail, with their case and edge, are the differences of part A; nothing else is.

   The table: for each control register one row for each value it takes together with each condition its next value depends on (the rows are the cases of the one-edge table), with the next value the design gives, from this run.

A4. The switches. In the table the needed next value is filled only in the rows that a failing point decides, with the sentence of the specification, the wait of the testbench or the need of another unit that says so. One failing point at a time, the earliest in the walk first:
   - Find the statements that decide the row (a condition, a compared value, a constant). Each place that could repair the row is a candidate: write it as a switch that changes this one place, in the source's form, with a name in `fix`.
   - Run the checker with the kept switches and one candidate at a time (a candidate is not in `SWITCHES` until it is kept; `fix="all"` means the kept switches: the checker and the other scripts turn "all" into the names in `SWITCHES`, so that a candidate is on only when it is named). What a candidate does to the handshake, to the wait of the testbench, to another case or to the data while waiting is read from the checker's print. A candidate is not accepted and not rejected by thought: a sentence such as "then the testbench would wait for ever" is a hypothesis until the checker has run with this candidate.
   - Keep the candidate with which the point holds and no point that held before fails; remove the other candidates from the model. If no candidate does this, two places may be one switch: name both, test them together, say so in the report. A new register is the last candidate, tried only when the print shows that no change of the existing statements repairs the row.
   - Where to look for candidates. When no sentence gives the needed next value: what the design already provides (a term of a condition that the walk never uses, a state that is never reached, a signal of the unit below that nothing waits for), marked "from the design, no sentence". When the unit must wait for a unit below: a control state in which the one-edge table says every data register is kept; if the end signal of the unit below already leads out of such a state, a candidate is to wait there and change only the condition that leaves it too early. The checker decides (P6 also holds while waiting). When the statement that decides the row also decides a row that agrees: the condition that separates the two rows, not the value both share. When the values the control register walks through and the values for which the one-edge table has a parameter inside its range are not the same set: the compared constants of the control register; the data path is not changed in part A.
   - When the checker prints the same for two candidates, take the one that changes less of the source; say that the other exists. From less to more: a constant or a condition of an existing statement; a signal that exists and was not used; a new signal or port taken from the unit below; a new register. The name, the place and the checker lines of a candidate that was removed stay in the notes.
   - A switch that was kept is not opened again in the same part unless the checker shows a point failing because of it; write each kept switch and the checker lines that decided it in the notes when it is kept.
   - After a switch that changes what an edge stores or which control values are walked, run the one-edge script again and bring it up to date (its cases, its switches), so that its print and its function describe the model with the kept switches.

A5. Part A is finished when the checker prints for every case that each of these points holds or has no requirement:
   P1. Without a start the control registers of this unit do not move and the handshake outputs are steady: they keep the value they have; which value this is, is not part of this point.
   P2. A start is accepted: in the edge of the start the row of the one-edge table is the one that takes the inputs, and the end follows.
   P3. A unit that must finish first is waited for, and the data registers of this unit are not written while waiting.
   P4. After the start the control registers leave the idle value, and they return to it once. The list of values the design walks through is the design, not the requirement: the checker does not hold it as the expected walk. Which values and how many are needed is decided by P5, P6, P7 and by part B.
   P5. The walk does not go through a control state in which the one-edge table says that a data register takes a value from a piece that has X or from a parameter outside its range (the rows the one-edge report left to be judged). This is read from the control state of each edge and the row of the table, not from the stored value: a value without X in the register does not show that the row was not used. The checker prints the control states of the walk and, for each, whether its row is one of these.
   P6. The end is signalled once for each operation, in the way the testbench or the module above waits for it (it waits for a rise: one rise after the start; it reads the level at each edge: it sees 1 after the start, and the count of edges is printed). The end signal is the statement "the result of the last start is there": from the edge after an accepted start until the result is complete it is 0 in every edge, also while the unit waits for a unit below. A signal that stays 1 from the operation before says the end to whoever reads its level.
   P7. The result is complete when the end is signalled. In every edge before which the end signal is already 1, until the next start, no part of the result (for a unit below: everything the module above reads) changes its value; the checker compares the value before and after each of these edges. The edge that makes the end signal 1 is not one of them: it may write the last part of the result. A part that is written again with the value it has does not change.
   P8. A second operation can start.
   A point that cannot be measured because another point fails (no end, so nothing to compare after it) is printed as "not measured, see Pn"; points that fail because of the same row of the table are one difference.
   A start while the unit is busy is run and printed; it has a point only when a sentence says what must happen, and the other points are not judged in this case. The registers of a unit below are printed and not judged: that unit has its own report. A point for which neither a sentence, the testbench nor the module above gives a requirement is written as "no requirement" and is not repaired.

## Part B — the sequence of operations, then the values

B1. The design's sequence is not written by hand. Take the control states the walk of part A goes through in one operation (from the run, edge by edge), and for each edge take from the one-edge table what the data registers take in that state: the pieces applied, in the order of the chain, each with its parameter (import the function of the one-edge script; when it has no row for a control state of the walk, or gives a parameter without the value it selects, add this to the one-edge script with one more measured edge and do not write the line by hand). Write them with a script as a flat list in a file: one line per operation applied to the data, from the load to the output; an edge in which the data registers keep their value gives no line. An operation has a parameter in its line only when the operation takes one (a key, an index, a constant it selects); do not number the lines.

B2. Write the specification's sequence in the same form and with the same words in a second file (from the step record of the reference model where it gives one). Compare the two files with the tool listdiff. It aligns the lists, so one extra line does not make every later line a difference. Each block it reports (extra, missing, different) is one difference.
   - The same operations cut into edges at other points give the same flat list: no difference.
   - Operations that may be exchanged without changing the result are not a difference; say which rule allows it and check it with a run.
   - A design that computes every part of a data register in every edge and is right when the end is signalled: reduce by destination. Keep for each part of the data register only the lines of the last edge that wrote this part before the end; equal lines for different parts are different lines. Do the reduction on pairs (destination part, line) and write only the line to the file. Say that the list then says nothing about the number of edges, and confirm with the values (B4).
   - When the reference model gives no step record for this unit, the specification's list is written from the algorithm of the specification; both lists then have the same author, so the values (B4) are the evidence.

B3. For each difference, the first in the list first: it belongs to one control state of the walk (the edge the line came from). Find the statement that decides what this state applies or which parameter it selects, and prove it with a switch that changes this one place. Run the one-edge script and part B1 again: the lists agree at this position. "The control must be redesigned" is not a result; the result is the line, the control state and the statement.

B4. When the lists are the same: run each case and compare the result with the reference model. The result is read where the source of the requirement reads it: the value in the cycle in which the end signal is 1, before the edge that samples it, not the value some edges after the walk. A result that is wrong there and right later belongs to the switch of part A that decides when the end is signalled: its candidates are run through the checker again (P7). If a result is wrong, find the first edge after which a data register differs from the reference's value at the same line of the list, and compare the pieces of that edge with their references as in the skill check-one-edge, point 3.

B5. Finished when, with all switches on, every case of this unit gives the handshake of part A, the two lists are the same, and the results equal the reference. The report ends with what this unit gives the module above: which signal says the end, in which edge, and what is complete from then on. Report the cases, the tables, the two lists and the print of listdiff, each switch with its source line, the change and the row or line it repairs, and which statements rest on a run and which on reading only.
